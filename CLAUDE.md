# Art du Kivu — Frontend

Next.js 16 (App Router) + React 19 + TypeScript strict + Tailwind 4. Consomme l'API Django REST d'Art du Kivu.

## Architecture — à savoir avant de toucher au code

- **Server Components** (`page.tsx` async) appellent l'API directement via `lib/api-client.ts` (`apiFetch`).
- **Client Components** appellent aussi `apiFetch`, mais celui-ci route automatiquement vers `/api/proxy` (`app/api/proxy/route.ts`) côté navigateur — jamais l'URL réelle de l'API, jamais le token manipulé côté client.
- **Auth** : `access_token`/`refresh_token` en cookies `httpOnly`, jamais en `localStorage`/JS. Le refresh est géré côté serveur (`lib/server/refreshAccessToken.ts`), déclenché automatiquement sur 401 par `/api/proxy` et `/api/auth/me`. Le refresh token tourne (`ROTATE_REFRESH_TOKENS` côté backend) — `applyRefreshedTokenCookies` doit toujours réécrire les deux cookies après un refresh, jamais juste l'access token.
- **`proxy.ts`** (racine) est la convention Next.js 16 de middleware (anciennement `middleware.ts`) — protège `/mon-profil` côté serveur (vérifie juste la présence des cookies, pas leur validité — la validation réelle reste dans `/api/proxy`/`/api/auth/me`). Ne pas confondre avec `app/api/proxy/route.ts` (notre proxy API interne) : coïncidence de nom, aucun rapport entre les deux fichiers.
- **`lib/api-types.ts` est la SEULE source de vérité pour les types de réponse API**, dérivée de `docs/Art_du_Kivu_API.yaml`. Ne jamais redéfinir un `interface ApiXxx` local dans un service, une page ou un fichier `types/*.ts` — ça a déjà causé des incompatibilités de types silencieuses, et la règle s'est déjà déliée deux fois (`ApiActivityEntry`/`ApiBadge`/`ApiChallenge`/`ApiPoll`, désormais migrés vers l'import central). Toujours `import type { ApiXxx } from "@/lib/api-types"`.
- **`lib/mappers.ts`** convertit les shapes API brutes vers les types frontend (`@/types/*`). Les commentaires inline documentent les écarts réels entre le spec OpenAPI et le comportement observé en prod (ex: `playback_hls_url` sans préfixe `cf_` après une migration Cloudflare→MediaMTX, `cover_url` au lieu de `image_url` sur les podcasts) — ces commentaires priment sur le YAML s'ils divergent.
- **Pattern de page** : `page.tsx` (Server Component) fait le fetch initial avec fallback vers `data/*.ts` en cas d'échec API, puis rend un composant client `XxxPageClient.tsx` qui reçoit les données initiales en props et gère l'interactivité (filtres, pagination "voir plus"). Confirmé encore valide sur `app/blog/`, `app/podcasts/`, `app/communaute/`, `app/evenements/`.
- **Type unique par liste, pas un par variante d'affichage** : pattern établi cette session sur Événements (`EventGridItem`) et Podcasts (`PodcastListItem`) — un seul type couvre le hero "à la une", l'aperçu compact et la liste complète/filtrée d'une même ressource, mappé une seule fois depuis l'API. Avant, chaque variante d'affichage (featured/sélection/récents/...) avait sa propre interface quasi identique, pontées avec des `as unknown as` non sûrs à l'usage. Reproduire ce pattern pour toute nouvelle page de liste plutôt que créer une nouvelle interface par carte.
- **Composants Mobile/Desktop** : plus de paires de fichiers dupliquées. Un seul composant par feature, soit unifié via des classes Tailwind responsive (`lg:`), soit via une prop `variant?: "mobile" | "desktop"` quand les layouts divergent réellement — jamais deux fichiers séparés pour la même feature.
- **Prompts/actions partagés à réutiliser, pas à réinventer** : `components/ui/AuthPromptModal.tsx` (connexion requise), `components/ui/ShareMenu.tsx` (partage natif + fallback WhatsApp/Facebook/X/Telegram/copie), `components/ui/ComingSoonModal.tsx` (fonctionnalité pas encore prête côté backend). Plusieurs composants avaient leur propre texte de prompt inline ou leur propre `navigator.clipboard.writeText` sans gestion d'erreur avant d'être migrés vers ces trois-là (Communauté, Événements, Podcasts) — ne pas réintroduire de variante locale.
- **`ContentImage`** (`components/ui/ContentImage.tsx`) est le seul point d'entrée pour afficher une image venant de l'API (upgrade `http://`→`https://` automatique, fallback si l'image est cassée). Passer les classes de taille/forme/position directement en `className` — le composant les applique sur son propre wrapper (`relative`/`absolute` + `overflow-hidden`), pas besoin d'un div englobant supplémentaire. Des divs `style={{ backgroundImage: url(...) }}` bruts existent encore par endroits (trouvées et corrigées sur la page podcast détail, puis sur `app/blog/[slug]/page.tsx`) — à chaque fois qu'on en croise une nouvelle, la remplacer par `ContentImage`.
- **`hooks/useLiveLoadingMessages.ts`** fait tourner un court message français ("Encore un moment...", etc.) pendant qu'un flux live (audio ou vidéo) charge/bufferise, réutilisé par `LivePlayer` (radio), `NowPlayingHero` (live-music) et `LiveStreamPlayer` (WebTV, `components/media/`) plutôt que chacun n'invente son propre texte de chargement. Ne l'activer que sur un état de chargement réel (`isLoading && !hasError`), jamais sur une erreur ou un état hors-ligne.

## Design system

Tailwind 4 en config CSS-first (`app/globals.css`, `@theme` — pas de `tailwind.config.*`). Valeurs réelles, à réutiliser telles quelles plutôt qu'en inventer de nouvelles :

- **Couleurs** (tirées du logo) :
  - `primary` `#E63012` (rouge-orange — CTA, accents principaux, focus rings), `primary-dark` `#B8240C` (hover)
  - `navy` `#0D2347`, `navy-mid` `#162E5C`
  - Fonds : `background-dark` `#12100F`, `surface` `#1A1714`, `surface-raised` `#221E1B`, `border` `rgba(230,48,18,0.12)`
  - Accents : `accent-teal` `#00A896`, `accent-gold` `#D4A843`, `accent-yellow` `#F5C518` — **`primary` n'est pas le teal**, ne pas confondre les deux dans le code ou des commentaires
  - Texte : `text-primary` `#F0EDE8` (blanc cassé), `text-muted` `#8A8178`, `text-faint` `#4A443E`
- **Typographie** : `font-display: "Epilogue"`, chargée via `<link>` dans `app/layout.tsx` (pas `next/font`) — d'où les warnings ESLint `no-page-custom-font` connus sur ce fichier, non bloquants.
- **Rayons** : `radius-lg: 1rem`, `radius-xl: 1.5rem`.
- **Tailles de texte mobile** : principe établi sur toutes les pages retouchées cette session (Artistes, Communauté, Événements, Podcasts) — modéré, jamais imposant ; titres de section en `text-base`/`text-lg`, jamais `text-xl`+ sur mobile ; métadonnées en `text-[10px]`/`text-xs`.
- **Classes utilitaires maison** (`globals.css`, pas du Tailwind pur) : `.kivu-texture`, `.glass-nav`, `.card-glow`, `.live-dot`, `.kivu-divider`, `.animate-fade-up`. `.hide-scrollbar` et `.no-scrollbar` font la même chose et coexistent (redondant) — `.no-scrollbar` est la plus utilisée dans le code récent.
- **Carrousels auto-défilants** : pattern établi cette session (Communauté défis, Événements "Prochainement", Podcasts "Récents") — `setInterval` + `scrollIntoView({behavior:"smooth"})` sur un conteneur `snap-x snap-mandatory`, avec indicateurs (dots). Réutiliser cette recette plutôt qu'une nouvelle lib de carrousel.

## Problèmes connus / dette technique restante

- **Double-mount HLS corrigé** sur `LivePlayer` (radio, `components/radio-en-direct/`) et `NowPlayingHero` (live-music, `components/liveMusic/`) : les deux étaient montés deux fois côté page (une fois par breakpoint, masqués en CSS), donc chacun faisait tourner deux flux HLS en parallèle. Pattern retenu : un composant `XxxProvider` (nouvel export nommé) possède désormais `useAudioLiveStream`/`useConsumptionHeartbeat` et l'unique élément `<audio>`, monté une seule fois autour des deux blocs `lg:hidden`/`hidden lg:block` de la page ; le composant par défaut (`LivePlayer`/`NowPlayingHero`) ne fait plus que lire cet état via Context et n'a plus de prop `show`/`track` — il peut donc être rendu deux fois (un par breakpoint) sans jamais recréer de flux. Si un nouveau composant live apparaît avec le même besoin (un breakpoint mobile et un desktop tous deux visuellement présents dans le DOM), reproduire ce pattern Provider/consumer plutôt que remonter le composant deux fois.
- Quelques shapes composites propres à une page/un composant restent définies en local plutôt que dans `lib/api-types.ts` : `app/page.tsx` (`ApiHomeData`), `app/mon-profil/page.tsx` (`ApiEarnedBadge`), `app/podcasts/page.tsx` (`ApiPodcastCategory`), `components/podcasts/GuestFollowButton.tsx` (`ApiSearchResult`), `app/top-artistes/page.tsx` (`TopArtist`), `app/top-morceaux/page.tsx` (`TopRelease`). Défendable tant que ce ne sont pas des doublons d'une entrée déjà présente dans `api-types.ts` — à surveiller si elles grossissent ou se dupliquent ailleurs. **`TopArtist`/`TopRelease` ont un vrai bug latent, pas juste une question de convention** : leurs noms de champs (`avatar_url`, `cover_image`, `artist_names`) ne correspondent pas aux vrais champs API (`ApiArtistList.photo_url`, `ApiRelease.cover_url`/`artist_name`) — déjà signalé par un commentaire existant dans ces fichiers. Ces deux pages affichent donc probablement des images/noms d'artiste vides en prod. Pas corrigé ici (aurait changé le comportement, hors scope d'un nettoyage mécanique) — à traiter comme un bug séparé.
- **`no-explicit-any` : 0 occurrence restante** (les ~130 précédemment documentées ont été éliminées). Ne pas relâcher cette discipline en ajoutant de nouveaux `any` non justifiés — `npx eslint .` doit rester à zéro erreur sur cette règle.
- **`.glass-nav` défini deux fois dans `app/globals.css`** (une fois vers la ligne 60 avec un fond navy translucide, une fois vers la ligne 154 avec `rgba(231,7,7,0.85)`, un rouge) — la seconde définition gagne la cascade, donc la classe rend actuellement en rouge. Ressemble à un résidu de copier-coller jamais nettoyé. Vérifier laquelle est réellement voulue avant de retoucher cette classe.
- Plusieurs pages retombent silencieusement sur des données mockées (`data/*.ts`) si l'appel API échoue, sans indicateur visuel (~20 fichiers concernés, dont `app/page.tsx`, `app/blog/*`, `app/communaute/*`, `app/podcasts/*`, `app/evenements/*`, `app/artistes/*`, `app/mon-profil/*`). Si un rendu semble "faux" en debug, vérifier d'abord si l'API a réellement répondu.
- **Commentaires** : `hooks/useEngagement.ts`/`components/ui/EngagementBar.tsx` (partagés par Communauté, podcasts, webtv, releases, emissions, live-music) paginent maintenant à 10 commentaires par page avec un bouton "Voir plus" — avant, un post populaire chargeait et rendait tous ses commentaires d'un coup dans une boîte à scroll interne. Ne pas revenir à un chargement complet si on retouche ce composant.
- Plusieurs endpoints retournent des données réelles mais incomplètes/mal formées (ex: `cover_url` tronqué sur certains podcasts, `image_url` en `http://` au lieu de `https://` sur certains événements) — le frontend absorbe déjà ça proprement (`ContentImage` upgrade le protocole et affiche un placeholder si l'image ne charge pas), mais ce n'est pas un bug frontend à re-corriger si on le revoit, c'est une question de qualité de données côté backend.
- **`lib/services/events.ts` n'a volontairement qu'une seule fonction** (`registerForEvent`), actuellement sans appelant : `BookingWidget.tsx` appelait ce endpoint pour la réservation de billets, mais la confirmation promise n'arrivait jamais réellement côté serveur, donc le composant affiche désormais un `ComingSoonModal` à la place (voir le commentaire sur les deux fichiers). Ne pas la re-brancher tant que le flux de réservation n'est pas vraiment supporté côté backend — et ne pas y ajouter de fonctions de liste/détail événements par erreur, ce n'est pas son rôle (`app/evenements/*` fait son propre fetch inline pour ça, c'est un choix distinct).
- **Les 5 pages catégories WebTV** (`app/concerts`, `documentaires`, `freestyles`, `interviews`, `studio-sessions`) sont des quasi-clones de `app/web-tv/page.tsx` (même endpoint `/api/v1/webtv/videos/?category=X`, juste le slug de catégorie/titre/copie qui change) — elles utilisent maintenant toutes `mapApiVideoToWebTVVideo` et `ContentImage` comme la page WebTV principale, plutôt que `ApiVideo` brut + `next/image`. Reproduire ce nettoyage sur toute nouvelle page catégorie du même genre plutôt que copier l'ancien pattern.
- **`/podcasts/shows/[slug]`** (nouveau) affiche un podcast au niveau "émission" (titre, description, cover, nombre d'épisodes) — distinct de `/podcasts/[slug]` qui reste une page épisode. `lib/services/podcasts.ts#fetchPodcastShowEpisodes` traite la réponse de `GET /podcasts/{slug}/episodes/` comme une liste paginée d'épisodes alors que le spec OpenAPI déclare (probablement à tort — l'operationId a un suffixe `_2` suspect) qu'elle renvoie le même objet `PodcastSeriesList` que `GET /podcasts/{slug}/`. La fonction gère les deux formes au runtime, mais si les épisodes n'apparaissent jamais sur cette page en prod, vérifier cette hypothèse en premier.

## Référence

`docs/Art_du_Kivu_API.yaml` = spec OpenAPI à jour du backend (source de vérité pour les shapes de réponse ; ~19 domaines de ressources : analytics, articles, artists, auth, community, emissions, events, gamification, health, home, live_music, media, newsletter, podcasts, radio, releases, search, users, webtv). `docs/archive/` contient d'anciens documents de suivi de projet, sans valeur de référence technique. `docs/COMMUNAUTE_BACKEND_REQUIREMENTS.md` documente les écarts encore ouverts entre la logique défis/talents/sondages voulue et ce que l'API supporte aujourd'hui.
